# API surface

Every endpoint an instance exposes, how to reach it, and exactly what gates access to
it. Generated by reading `terraform/api.tf`, `terraform/cloudfront.tf`,
`src/lambda/api/router.ts` and `src/lambda/api/auth.ts` directly — if this drifts from
those, they're authoritative, not this doc.

## Two ways to reach the metadata API

Every route below is served by **one Lambda** (`terraform/api.tf`, `src/lambda/api/router.ts`)
behind **one API Gateway HTTP API**, reachable two ways:

1. **Through CloudFront**, at `https://<domain>/api/*` — the public, documented path.
   A CloudFront Function (`strip_api_prefix` in `cloudfront.tf`) strips the `/api`
   prefix at the edge before forwarding to the API Gateway origin. This behavior
   forwards every viewer header except `Host` (`Managed-AllViewerExceptHostHeader`),
   specifically so `Authorization` reaches the Lambda, and caching is disabled
   (`Managed-CachingDisabled`) since every response here is per-user.
2. **Directly at the API Gateway invoke URL** (`https://<api-id>.execute-api.<region>.amazonaws.com/`,
   no `/api` prefix) — works identically, since the JWT authorizer and routes live on
   the API Gateway resource itself, not on CloudFront. CloudFront adds nothing here
   except a stable custom domain and TLS; it isn't in the trust boundary.

Both paths enforce the same access control, described below.

## Access control

**The JWT authorizer** (`aws_apigatewayv2_authorizer.jwt` in `api.tf`) sits in front of
every route except `GET /health`. It verifies the token's signature and expiry against
the instance's own Cognito user pool (`issuer = https://cognito-idp.<region>.amazonaws.com/<pool-id>`)
and checks the audience against the app client ID. That audience check is satisfied by
either token Cognito issues: an ID token's `aud` claim, or an access token's `client_id`
claim — API Gateway's JWT authorizer treats them interchangeably for a Cognito issuer,
so either token works as a bearer credential.

**What the authorizer does *not* do**: resolve an ownerId, or check library membership.
That's `src/lambda/api/auth.ts`, run inside the Lambda on every authorized request:

```
JWT (verified by API Gateway)
  → { issuer, subject } from the iss/sub claims
  → IDP#<issuer>#<sub> pointer lookup            → userId
  → membership lookup for that userId            → ownerId, role
```

A valid, unexpired JWT from a stranger who has never signed in resolves no pointer and
gets `401 unknown identity`. A JWT for someone who signed in but was later removed from
their library resolves no membership and gets `403 no library membership` — this check
runs fresh on every call, uncached, specifically so a revoked membership takes effect on
the very next request rather than waiting out a token's lifetime.

**Three `authMode` values** (`router.ts`), applied per route below:

| Mode | What the handler receives | Routes |
| --- | --- | --- |
| `none` | Nothing — no JWT involved at all | `GET /health` only |
| `identity` | `{ issuer, subject }`, not yet an ownerId | `POST /session/bootstrap` only — this is the route that *creates* the pointer, so it can't require one to already exist |
| `owner` | Full `{ userId, ownerId, role }`, resolved as above | Everything else |

No handler ever accepts an `ownerId` from the request body or path — every `owner`-mode
route gets it from the resolved JWT, never from client input. That's the entire
authorization model in one sentence.

## Routes

| Method & path | What it does | Access |
| --- | --- | --- |
| `GET /health` | Liveness check — `{"status":"ok"}` | **None.** No JWT checked at all. |
| `POST /session/bootstrap` | First-sign-in handshake: resolves or creates the `IDP#` pointer and the owner's library, idempotently. Every client calls this once per sign-in. | **JWT required, no ownerId yet** (`identity`). This is the one route reachable by anyone with a *valid* Cognito token but no library — by design, since it's what creates one. |
| `GET /keys` | Lists the caller's key wrappings (metadata only — device label, kind, `masterKeyVer`; never another device's unwrapping material). | Owner |
| `POST /keys` | Uploads a new key wrapping (device, passkey, or recovery) against the owner's *current* master key version, which the server derives — never accepts a client-supplied `masterKeyVer`. | Owner |
| `DELETE /keys/{wrapId}` | Removes a key wrapping (e.g. de-enrolling a lost device). | Owner |
| `POST /keys/version` | Atomically mints the next master key version (`mk-<n>`) — called once at first enrolment or at rotation, never per-device. | Owner |
| `GET /keys/hash-secret` | Returns the owner's wrapped `hashSecret` (`encHashSecret`/`hashSecretKeyId`) — a device with the master key unwraps it the same way it would a DEK. `404` until the first device has ever called the `PUT` below. | Owner |
| `GET /settings` | Returns the owner's non-secret `#SETTINGS` fields (`homeTz`, `stripLocationOnUpload`, …) — every client reads this before enqueueing uploads, the same way it already needs `homeTz`. | Owner |
| `PATCH /settings` | Updates one or more owner settings. v1 only accepts `stripLocationOnUpload` — deliberately narrow, not a generic patch of every `#SETTINGS` field (`homeTz` still has no edit path; out of scope here). | Owner |
| `PUT /keys/hash-secret` | Stores the owner's wrapped `hashSecret`, used to HMAC `contentHash` for dedup. | Owner |
| `POST /uploads` | The stem/hash handshake: validates client-asserted metadata, checks for an existing live/trashed/purged match by content hash, creates or attaches to an asset, and returns **presigned S3 PUT URLs** for the ciphertext and thumbnails. | Owner |
| `GET /photos` | Timeline page, paginated. `from`/`to` (supplied together) bound it to a time range; `order=asc` returns that range oldest-first, which is what a client loading the page immediately *newer* than its cache needs. | Owner |
| `GET /photos/bounds` | Oldest/newest `takenAt` in the live timeline — the fast-scroll range for the Android client's timeline scrollbar. `ETag`/`If-None-Match`; 304 when unchanged. | Owner |
| `GET /photos/histogram` | Live photos per local day, plus the total — what the scrollbar weights itself by (design.md pattern 15). `ETag`/`If-None-Match`; 304 when unchanged. | Owner |
| `GET /photos/{photoId}` | Single asset detail. | Owner |
| `GET /photos/by-path?path=<path>` | Resolves one exact path (the same string a rendition's own `path` field holds, e.g. `-1739773001/IMG_1234.jpg`) straight to `{photoId, renditionId}` — one consistent `GetItem` against the PATH pointer (design.md pattern 1b), nothing else. Works for a trashed asset too, since trashing never touches PATH pointers. `404` if nothing is filed under that exact path. Doesn't return detail itself — chain to `GET /photos/{photoId}` for that, which already answers the same for live or trashed. Meant for a caller that already has an exact path in hand (a rename target, a local import tool's own computed path) and would otherwise have to page through `GET /photos`/`GET /trash` just to turn it into a photoId. | Owner |
| `PATCH /photos/{photoId}` | Manually corrects `takenAt`/`tzOffsetMin` — body `{takenAt, tzOffsetMin}`. Rewrites `#META`, `timelineSk`, every facet item's own `takenAt`/`facetSk`, and (live assets only) moves the photo's histogram bucket — one transaction (design.md "Known limitations"). Sets `takenAtSrc`/`tzSrc` to `manual`, which outranks every automatic rung (`paths.ts`'s `TAKEN_AT_SRC_RANK`), so a later-attached rendition's own EXIF never silently overwrites it. Works on a trashed asset too. | Owner |
| `PATCH /photos/{photoId}/renditions/{renditionId}` | Rendition mutation (currently: rename via path). | Owner |
| `POST /photos/{photoId}/renditions/{renditionId}/replace` | Replaces this rendition's stored bytes in place — body `{contentHash, plainBytes, bytes, mime, width, height, encIv?, encChunkSize}`, response `{uploadUrl}` (a presigned PUT against the rendition's existing S3 key — no CloudFront cache to dodge, unlike thumbnail repair, since `/media/*` is `caching_disabled`). Swaps the HASH pointer to the new content hash; updates `#META`'s `mime`/`width`/`height` too when this rendition is primary. For correcting the original's own stored content — an orientation baked in wrong, say — as opposed to `PATCH .../thumbs`' derived thumbnails or `PATCH /photos/{photoId}`'s plaintext metadata. Doesn't touch thumbnails itself; a caller wanting those regenerated makes its own follow-up call to `POST .../thumbs`. Refuses (409) an asset that's trashed, or new content that collides with different already-live content elsewhere. | Owner |
| `DELETE /photos/{photoId}` | Trashes an asset (soft delete, tombstone). | Owner |
| `DELETE /photos/{photoId}/renditions/{renditionId}` | Trashes one rendition; trashing the last rendition trashes the asset. | Owner |
| `POST /photos/{photoId}/restore` | Restores a trashed asset before it's purged. | Owner |
| `POST /photos/{photoId}/thumbs` | Repairs one or more thumbnail rungs on an already-uploaded asset: same "descriptors in, presigned PUT URLs out" shape as `POST /uploads`' thumbnail handling — see "Changing the ladder later" in design.md for why this has to be client-driven (the server never holds plaintext pixels). Merges into the existing `#META.thumbs` map rather than replacing it, so resending just the broken size(s) never erases a still-good one. Presigns against a **fresh** S3 key per call (`th/<ownerId>/<photoId>/<generation>/<size>`), not the plain upload-time key — that key is cached 1 year at the CloudFront edge (`terraform/cloudfront.tf`'s `thumbnails_immutable` policy), so overwriting it in place would leave already-cached edges serving the broken response for up to a year regardless of what S3 now holds. The old key is left orphaned in S3, not cleaned up. | Owner |
| `GET /trash` | Lists trashed assets pending purge, including any blocked-re-upload-attempt counters. | Owner |
| `GET /facets` | Facet vocabulary (labels, cameras, devices, years). | Owner |
| `GET /facets/{type}/{value}` | Assets matching one facet value, paginated. | Owner |
| `GET /devices` | Lists the owner's device config items (one per camera `deviceKey` — label, timezone default if set, photo count). | Owner |
| `PATCH /devices/{deviceKey}` | Edits a device's `label` and/or `tzOffsetMin` (an explicit `null` clears the default). 404s on a `deviceKey` ingest has never seen. | Owner |
| `DELETE /devices/{deviceKey}` | Removes a device config item — cosmetic only, since no photo references it back; ingest re-registers the device (with no offset) the next time it sees that `deviceKey`. Idempotent. | Owner |
| `DELETE /account` | Deletes the caller's entire library — media rows, S3 objects, the owner-registry entry. Requires the caller to echo back their own ownerId as an explicit confirmation, not just a bare call. | Owner |

## What isn't behind the API Gateway JWT authorizer at all

Three more surfaces are reachable through the same CloudFront distribution but never
touch the API Gateway or its authorizer:

| Path | Backend | Access |
| --- | --- | --- |
| `/.well-known/archivist.json` | S3 (`web` bucket), via the default cache behavior | **Public, unauthenticated, by design** — see "The app must find the backend" in `deployment.md`. Contains no secrets, only the pool ID, client ID and API base a client needs to *attempt* a login. |
| `/media/*` (→ S3 key `raw/…`) | S3 (`originals` bucket), via OAC, prefix stripped at the edge | **Unauthenticated at the CDN layer.** No JWT, no signed URL, no CloudFront signed cookie. What's actually served is client-side ciphertext under a ULID-derived key with no directory listing — the protection is "unguessable key + the bytes are useless without the master key," not access control. Anyone who somehow obtained an exact object key could fetch the ciphertext (and only the ciphertext) without signing in. |
| `/thumbs/*` (→ S3 key `th/…`) | S3 (`derived` bucket), via OAC, prefix stripped, cached 1 year at the edge | Same model as `/media/*`. |

**Uploads never go through CloudFront at all.** `POST /uploads` returns presigned S3 PUT
URLs (`presignPut` in `src/core/s3.ts`); the client `PUT`s ciphertext bytes directly to
S3 using AWS SigV4 query-string auth baked into that URL (short expiry, scoped to one
object). CloudFront's `/media/*` and `/thumbs/*` behaviors only allow `GET`/`HEAD` — they
exist for reads, not writes.

**Worth naming directly**, since it's easy to read "unauthenticated" as a gap: it isn't
one here specifically because the payload is ciphertext the server never holds a key
for. The same pattern would be a real hole for plaintext content.
